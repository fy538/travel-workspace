# Contribution Contract Fixture Pack

## Question or outcome

Can Vesper turn a question, observation, artifact, invitation, social trace, or
correction into immediate differentiated value without creating homework,
hidden memory, false lived truth, or unauthorized consequence?

This pack operationalizes the recommendations in [Contribution authority,
immediate value, and repair
research](contribution-authority-immediate-value-and-repair-research-2026-08-29.md).
It is a product and structural-derivation artifact, not a claim that the target
responses are implemented.

The first ten experience fixtures compare:

1. **ChatGPT documented baseline** — what current official product
   documentation establishes that ChatGPT can use or control;
2. **current Vesper code envelope** — what repository contracts and prompts
   permit today, without inventing a live response;
3. **target Vesper contract** — the first-turn experience and the governed state
   transition it requires; and
4. **structural delta** — why the value depends on Vesper's objects,
   consequence model, multiplayer authority, or causal repair rather than on
   better chatbot prose.

Eight additional policy-pressure fixtures certify Ask/Bring legibility, expiry,
Outcome causality, affected-person projection, contextual inspectability,
purpose, and connected-service boundaries. They test state transitions rather
than specimen copy or a point-in-time competitor response.

## 1. Evidence discipline

Use these labels throughout:

| Label | Meaning |
| --- | --- |
| **DOCUMENTED** | Supported by current official product documentation |
| **CODE-EVIDENCED** | Present in local contracts, prompts, UI, routes, or tests; not necessarily deployed |
| **TARGET** | Proposed product behavior and required architecture |
| **STRUCTURAL** | Inference that follows from documented capability, product canon, and required state transitions |
| **NOT ESTABLISHED** | Not supported by the cited documentation or code; absence of evidence is not a claim of product impossibility |

Three rules prevent a misleading comparison:

1. Do not write specimen prose for “current ChatGPT” or “current Vesper.” The
   former is a documented capability floor; the latter is a code and migration
   envelope. Neither is the reference design.
2. Infer differentiation from required state and authority, not from whether a
   point-in-time product happens to produce weaker copy. A target that wins only
   on prose does not pass.
3. Keep answer quality separate from consequence quality. A fluent answer does
   not prove correct retention, canonical reconciliation, audience, or repair.
4. Treat “not documented” precisely: it establishes that a capability is not
   part of the cited baseline, not that another product could never build it.

## 2. The proposed contribution contract

### 2.1 Human gestures

| Gesture | Default interpretation |
| --- | --- |
| **Ask** | Use authorized context to answer; create no new durable Life object |
| **Point** | Treat the person's explicit observation as a private, source-bound attention trace; do not infer identity or preference |
| **Bring / Import** | Admit the source privately, interpret provisionally, return value, and show correction or Undo |
| **Keep** | Retain the named source, interpretation, intention, or outcome privately |
| **Share / Address / Invite** | Prepare a bounded audience consequence; preserve authorship; cross the audience boundary only under explicit authority |
| **Decide / Act** | Apply only the named consequence through its owner when authority and reversibility permit it |
| **Correct / Release** | Repair the named relation and invalidate dependent state |

### 2.2 Five authority axes

Every fixture resolves the structured meaning of:

- **Use:** immediate job, permitted purposes, and eligible consumers;
- **Retention:** independent Source, claim, and projection lifecycles;
- **Inference:** semantic scope, learning target, and learning level;
- **Audience:** contributor, subject or affected principal, custodian, and
  recipients; and
- **Action:** what real or canonical consequence may occur.

### 2.3 Three visible treatments

| Code | Treatment | User experience |
| --- | --- | --- |
| **T0** | Answer or prepare privately | Immediate value, no workflow, optional trust footprint |
| **T1** | Apply privately, then receipt | Value first; compact scope plus Correct or Undo |
| **T2** | Preview the material boundary | One prepared effect and one decision at audience, affected-person, spend, provider, public, sensitive-inference, or weak-reversal boundary |

Internal policy may remain more granular. These are presentation treatments,
not replacements for the consequence modes.

## 3. Evaluation rubric

Score each output from 1–5. A hard failure overrides the total.

| Dimension | The question |
| --- | --- |
| **Immediate utility** | Did the person receive useful value before any input, review, or classification request? |
| **Novelty** | Did the system add a reconstruction, mechanism, distinction, relation, or capability beyond the input? |
| **Truth discipline** | Did it distinguish source, plan, occurrence, outcome, inference, and unknown? |
| **Situated fit** | Did Place, Moment, people, Occasion, Plan, or current conditions materially improve the result? |
| **Consequence fit** | Did it stop, prepare, apply, or ask at the correct boundary? |
| **Effort** | How much confirmation, correction, or maintenance did it demand? Lower burden scores higher. |
| **Trust footprint** | Could the person tell why the consequential claim or action existed? |
| **Repairability** | Could the exact wrong relation be corrected without understanding system nouns? |
| **Non-creepiness** | Did it avoid identity reads, faux intimacy, hidden reuse, and performative memory? |
| **Multiplayer integrity** | Where applicable, did it preserve author, audience, private context, and plural Outcomes? |

Hard failures:

- repeats the person's contribution as if it were new;
- asks the person to supply the primary value;
- silently converts attention into personality or preference;
- treats a ticket or reservation as proof of attendance;
- widens audience or acts externally without authority;
- hides what was retained or makes it materially difficult to repair;
- merges people's private experience into one group interpretation;
- leaves deleted or corrected evidence active downstream; or
- claims a current Vesper behavior that is only architectural intent.

## 5. Fixtures

## F01 — Practical live answer with no new retention

### Scenario and controlled evidence

The person has an already-authorized Sorrento–Amalfi ferry ticket in their
private journey. The test harness supplies:

- ticket: departure 12:05 from Sorrento;
- provider snapshot: on time, checked two minutes ago;
- route snapshot: ferry 42 minutes; fastest road alternative 78 minutes;
- hotel-to-port route: 18 minutes under current conditions; and
- no new artifact in this turn.

### Input

> Is my 12:05 ferry still the best way to Amalfi?

### Authority

```yaml
gesture: ask
immediate_job: act_now
use: current_ticket + provider_status + route + present_moment
retention: no_new_retention
inference: turn_only
audience: private_owner
action: none
treatment: T0
```

### ChatGPT documented baseline

**DOCUMENTED:** With memory enabled, ChatGPT can use relevant chats, files,
memories, and eligible connected-app context. With browsing or connected travel
data, it may answer from current information. Its memory UI can show some
personalization sources.

**STRUCTURAL implication:** finding a ticket, checking current conditions, and
answering without a write are the assistant capability floor. F01 is necessary
table stakes for Vesper, not differentiation by itself.

### Current Vesper code envelope

**CODE-EVIDENCED:** Concierge has current itinerary, transport, Place, temporal,
and location-context tools. It can answer without a canonical mutation. Tool
coverage and production freshness remain unverified externally.

**Risk:** ordinary conversation persists, and unrelated signal capture can run
in the background even when no durable personal consequence is needed.

### Target first turn

> **Keep the 12:05 ferry.** It is running on time, and the fastest road option
> is currently 36 minutes slower. Leave for Marina Piccola by 11:35; the route
> from the hotel is about 18 minutes.
>
> Ticket + operator + route · checked 2 min ago

No question, save control, or reflective continuation follows.

### Receipt and repair

- No durable-change receipt because nothing changed.
- The trust footprint opens the ticket, provider timestamp, and route.
- “Wrong hotel” or “different departure” recomputes the answer; it does not
  create a memory correction.

### Pass condition

The person can leave the app knowing what to do. No new Life object, preference,
or “ferry person” interpretation exists.

## F02 — “Sorrento has cliffs”

### Scenario and controlled evidence

The person is in a private Chat and deliberately points out:

> Sorrento has cliffs.

The source pack contains a University of Naples geology account: the Sorrento
plain is Campanian Ignimbrite deposited roughly 39,000 years ago; the tuff
coastal wall is approximately 50–100 meters high and retreats through wave
undercutting and collapse. See [DISTAR, University of
Naples](https://www.distar.unina.it/it/terremoti/shakemap?catid=25&id=132%3Acalcari-e-ignimbrite&view=article).

### Authority

```yaml
gesture: point
immediate_job: understand_now
use: user_observation + current_place + verified_geology
retention: private_source_bound_attention_trace
inference: source_local_place_relation
audience: private_owner
action: apply_reversible_private_trace
treatment: T1
forbidden: [visit_claim, preference_claim, identity_claim, public_place_contribution]
```

### ChatGPT documented baseline

**DOCUMENTED:** ChatGPT may remember conversational details and use web or
connected context to explain the observation. It can show memory sources and
accept a correction.

**NOT ESTABLISHED by the documented baseline:** a durable distinction between
the person's authored observation, the system's geological contribution, and
the future authority of each. That governed distinction is the structural delta.

### Current Vesper code envelope

**CODE-EVIDENCED:** Ordinary Concierge Chat can call `observe` immediately for
something considered worth remembering. The current prompt explicitly permits
preference, “personality insight,” context, emotional investment, and inferred
patterns, with no required visible admission receipt.

Intake v2 is safer for an explicitly shared text source: the candidate remains
private, source-bound, advice-only, and unable to self-grant retention. The two
paths currently express different philosophies.

### Target first turn

> **Sorrento is standing on the deposit of an ancient eruption.** Campanian
> Ignimbrite filled an older basin here about 39,000 years ago; the sea later
> cut that relatively level tuff terrace into the 50–100 meter wall the town
> sits above. The dramatic edge is both volcanic construction and continuing
> wave erosion.
>
> Kept as a private Sorrento observation · no visit or preference inferred ·
> Correct · Undo

### Receipt and repair

- `Correct` offers “different Place,” “do not keep this observation,” and
  “keep the observation but do not use it later.”
- `Undo` removes the derived attention trace without pretending to delete the
  already-persisted conversation message.
- The source and Vesper's geology explanation remain distinguishable.

### Pass condition

The explanation is valuable without opening it, and later Vesper may use “the
Sorrento cliff observation” as a bridge. It may not infer that the person likes
cliffs, seeks thresholds, or visited a specific cliff.

## F03 — Ferry ticket as planned evidence, not lived truth

### Scenario and controlled evidence

The person drops a ferry-ticket screenshot into private Chat. The pack supplies:

- ticket: Sorrento → Amalfi, scheduled 12:05–13:20;
- checkout photograph timestamp: 11:10 in Sorrento;
- Amalfi hotel confirmation timestamp: 14:36;
- no boarding scan or geolocation evidence; and
- no competing transport artifact for the interval.

### Authority

```yaml
gesture: bring
immediate_job: understand_now
use: imported_ticket + private_journey_evidence
retention: private_source_and_derived_candidate
inference: journey_local_reconstruction
audience: private_owner
action: apply_reversible_private_artifact
treatment: T1
truth_boundary: scheduled_not_occurred
```

### ChatGPT documented baseline

**DOCUMENTED:** ChatGPT can read a file or image, use memory and other relevant
files, summarize ticket details, and personalize the response.

**NOT ESTABLISHED by the documented baseline:** a typed transport artifact with
separate scheduled and occurred truth, evidence lineage, journey projection,
and correction that can retain the ticket while retracting the occurrence.

### Current Vesper code envelope

**CODE-EVIDENCED:** Share capture uses Intake v2, private custody, source refs,
normalization, semantic candidates, and detailed correction paths. When
continued into Chat, the pending turn requests `answer_only`. The share-capture
UI currently asks the person to “Keep this interpretation,” correct it, or
remove the share.

**Gap:** the first Chat response does not yet guarantee the journey
reconstruction or family-specific context consequence. The explicit keep/review
screen is more homework than the target private reversible default.

### Target first turn

> **This ticket closes the only undocumented transition between Sorrento and
> Amalfi.** Your last Sorrento trace is 11:10 and the first Amalfi record is
> 14:36; the 12:05 ferry fits that gap. It proves the scheduled route, not that
> you boarded.
>
> Added privately to the Southern Italy journey · Scheduled · Correct · Undo

### Receipt and repair

- `I did not go` preserves the purchased ticket and retracts the occurrence.
- `Wrong date`, `not my ticket`, and `separate from this journey` repair only
  the relevant binding.
- `Delete source` removes the screenshot and invalidates its dependent claims.

### Pass condition

The person receives a useful reconstruction immediately and is not asked to
approve obvious private organization. The interface never renders “you took
the ferry” without stronger evidence or confirmation.

## F04 — Pasta photograph: mechanism without psychography

### Scenario and controlled evidence

The person brings a menu photograph and a dish photograph from the same table,
then says:

> Pasta here tastes different.

The menu names cacio e pepe. A verified research source explains that starch
concentration and temperature affect the stability of the cheese-water sauce;
below a sufficient starch concentration, proteins aggregate and the sauce can
separate. See [Phase behavior of Cacio e Pepe
sauce](https://arxiv.org/abs/2501.00536).

### Authority

```yaml
gesture: bring_and_point
immediate_job: understand_now
use: menu_photo + dish_photo + user_observation + culinary_source
retention: private_sources_and_source_bound_observation
inference: dish_local_mechanism
audience: private_owner
action: apply_reversible_private_artifact
treatment: T1
forbidden: [ate_claim, liked_claim, restaurant_visit_claim, identity_claim]
```

### ChatGPT documented baseline

**DOCUMENTED:** ChatGPT can analyze images, research or explain culinary
mechanisms, remember stated preferences, and use past context.

**NOT ESTABLISHED by the documented baseline:** durable source-role separation
among the person's observation, the menu claim, photograph evidence, system
explanation, and any future preference inference.

### Current Vesper code envelope

**CODE-EVIDENCED:** Intake supports dining and attention artifact families with
truth modes, evidence locators, missing fields, and correction. Concierge's
legacy memory prompt may also record food preference or a generalized personal
observation in the same turn.

**Gap:** source-bound explanation and the visible “did not infer preference or
consumption” boundary are not guaranteed in the first response.

### Target first turn

> **Part of the difference is temperature control, not a hidden ingredient.**
> The menu identifies cacio e pepe; its smoothness depends on enough starch to
> keep the cheese-water mixture stable and on avoiding heat that makes the
> proteins clump. The photograph supports the glossy texture, but it cannot
> prove who ate it or whether you liked it.
>
> Menu + photograph kept privately · observation attached · Correct · Undo

An optional depth aperture may show the mechanism or an at-home technique. It
does not ask “Want to remember this?”

### Receipt and repair

- “Not my dish,” “different restaurant,” “keep photos but forget observation,”
  and “delete originals” are separate.
- A later “I hated it” can coexist as authored meaning; it does not invalidate
  the sauce mechanism.

### Pass condition

The person can explain one concrete reason for the difference. No unsolicited
“you are becoming a discerning eater” or “you love authentic pasta” appears.

## F05 — The Odyssey, Aeneas, and Augustan political use

### Scenario and controlled evidence

The person previously imported a movie ticket for *The Odyssey*. Later, after
seeing the Troy-to-Rome tradition at the Colosseum, they ask:

> I already understand that Aeneas connects Troy to Rome. What is the part I am
> missing?

The source pack contains scholarship on the Julian descent claim, Virgil's
*Aeneid*, and the Augustan monumental program. Cambridge's introduction to
*Reading Virgil* documents the Iulus–Julian lineage and the poem's Augustan
genealogical function; Smarthistory situates Augustan monuments as coordinated
public claims about power, legitimacy, peace, and dynasty. The latter also
records the dispute over whether the Ara Pacis sacrifice panel depicts Aeneas
or Numa. The target must not depend on resolving that disputed figure.

### Authority

```yaml
gesture: ask
immediate_job: understand_now
use: explicit_known_claim + prior_movie_ticket + current_place + verified_research
retention: no_new_retention
inference: turn_only_relational_mapping
audience: private_owner
action: none
treatment: T0
known_to_person: [Aeneas_connects_Troy_to_Rome]
```

### ChatGPT documented baseline

**DOCUMENTED:** ChatGPT can use prior chats, files, and memories to personalize
the historical answer and can research the topic when tools are available.

**STRUCTURAL implication:** a general assistant with sufficient context can
produce the same historical paragraph. F05 differentiates Vesper only when the
known-to-person boundary and resulting Place/Life continuity improve future
openings without turning one question into a personality verdict.

### Current Vesper code envelope

**CODE-EVIDENCED:** Source refs, prior conversation retrieval, Place context,
and seeded cultural content can enter Concierge context. The new Editorial
Canon forbids parroting and defines a known-to-person check.

**Gap:** the contribution brief and semantic-receipt/exposure check are not yet
a general runtime gate before response generation.

### Target first turn

> **Augustus turned Trojan ancestry into an argument for who should rule
> Rome.** The Julian family claimed descent through Aeneas's line; Virgil's
> *Aeneid* connected that family story to Rome's destiny, while the Augustan
> building program made dynasty, piety, and public order visible together. The
> myth did not merely explain Rome's origin—it helped naturalize a new political
> order.
>
> Built from the movie ticket, your Colosseum question, Virgil, and Augustan
> material evidence · Sources

### Receipt and repair

- This is an answer, not a newly retained personal belief.
- The source inspector separates ancient text, family claim, modern scholarly
  interpretation, and disputed monument identification.
- If the person later says “I already knew that too,” that new explicit
  statement is handled as its own Point/Correct turn. Vesper must disclose any
  bounded known-to-person update rather than silently retaining it or turning
  it into negative preference feedback.

### Pass condition

The response advances beyond the user's connection and offers a bounded
mechanism. A title such as “Rome adopted the survivor's side” is a failure.

The person imports a provider message while traveling alone. The harness
supplies:

- confirmed room and 15:00 nominal check-in;
- new message: staffed reception closes at 14:00;
- current arrival estimate: 14:40;
- the same provider thread contains verified self-check-in instructions; and
- no shared Plan or affected companion.

### Authority

```yaml
gesture: import
immediate_job: reconcile
use: reservation + provider_change + arrival + access_instructions
retention: private_source_and_updated_commitment_evidence
inference: commitment_local
audience: private_owner
action: apply_reversible_private_plan_update
treatment: T1
external_contact: not_required
```

### ChatGPT documented baseline

**DOCUMENTED:** With eligible Gmail or file context, ChatGPT memory can use
upcoming travel confirmations to personalize an answer. It may synthesize the
email and advise what to do.

**NOT ESTABLISHED by the documented baseline:** reconciliation into one
canonical commitment with provider truth, planned state, and later lived outcome
kept separate—and withdrawal of the obsolete assumption from every projection.

### Current Vesper code envelope

**CODE-EVIDENCED:** Intake can custody forwarded messages; Plan, stay, provider,
live-repair, receipt, and canonical-readback substrates exist. Grounded live
Plan repair is dark by default and production-unverified. Generic admission
does not itself authorize the stay owner mutation.

### Target first turn

> **The room is still confirmed, but staffed check-in now closes 40 minutes
> before you arrive.** The provider included self-check-in instructions in the
> same thread, so no call is needed unless the keypad code fails.
>
> Arrival updated with self-check-in · old reception assumption withdrawn ·
> Provider message · Undo

If no verified self-check instructions existed, Vesper would prepare a message
or call and use **T2** before contacting the provider.

### Receipt and repair

- `Undo` restores the prior Plan projection only if provider truth has not made
  it invalid; otherwise it offers a correction rather than a dishonest revert.
- “Wrong reservation” detaches the message and recomputes the commitment.
- Provider contact, if needed, requires explicit execution authorization.

### Pass condition

The person receives relief, not a summary followed by “Would you like me to
help?” The old check-in assumption does not survive on another surface.

## F07 — Authorized Rome–Paris social mosaic

### Scenario and controlled evidence

Maya has shared one Paris evening trace with her friends: a Seine route,
timestamped photographs, and a short authored caption. The person has a private
Rome evening trace. The harness supplies:

- Rome at 21:00: 31°C; photographs near fountains and late street tables;
- Paris at 21:00: 24°C; Maya's route follows the Seine;
- Maya's evidence audience: friends, including this person; and
- no permission to repost, publish, or quote private material.

The person asks:

> Was there anything interesting about Maya being in Paris while we were in
> Rome?

### Authority

```yaml
gesture: ask
immediate_job: compare
use: own_private_trace + Maya_friend_visible_trace + weather
retention: no_new_personal_or_shared_memory
inference: bounded_social_mosaic
audience: private_projection_to_requester
action: none
treatment: T0
forbidden: [public_share, group_mind, relationship_score, Maya_private_meaning]
```

### ChatGPT documented baseline

**DOCUMENTED:** ChatGPT can use memories, chats, and connected material that the
user has access to. Its documentation does not establish a Vesper-like
friend-authored audience projection or plural Outcome model.

**NOT ESTABLISHED by the documented baseline:** a friend-authored object whose
original author, audience, revocation rights, and bounded use survive retrieval
into another person's private projection.

### Current Vesper code envelope

**CODE-EVIDENCED:** Group-safe composition, actor-bound personal memory,
relationship openings, Occasion invitations, audience projections, and social
artifact fixtures exist. The one permissioned relationship opening is dark by
default; broad personal-Chat social mosaics are not claimed shipped.

### Target first turn

> **The same hot evening produced two different public lives.** At 9 p.m. your
> Rome route was still 31°C and stayed near fountain edges and late tables;
> Maya's Seine walk had fallen to 24°C and kept moving along the river. The
> contrast is not simply Rome versus Paris—it is how temperature and public
> space changed what an evening could hold.
>
> Your private Rome trace + Maya's friends-visible Paris trace · Maya's words
> remain hers · Sources

### Receipt and repair

- No message is sent and no shared memory is created.
- “Don't use Maya's activity this way” disables this use for the requester; it
  does not mutate Maya's source authority.
- Maya can revoke the original audience and invalidate the comparison.
- “Address Maya” would prepare a human-authored handoff and cross into T2.

### Pass condition

Removing Maya's trace destroys the comparison's value. The output neither
reports “your friend was also in Europe” nor claims what the evening meant to
either person.

The host says:

- route: shaded market entrance; taxi at 10:20; outdoor walk under six minutes;

### Authority

```yaml
gesture: decide_and_invite
immediate_job: coordinate

```

**NOT ESTABLISHED by the documented baseline:** a bounded Occasion with

### Current Vesper code envelope

- After send: each invite has its own pending/accepted/declined/deferred state.
- Maya and Theo receive no explanation naming the other's or their own private

- Removing a participant revokes future projections but preserves historical
  invitation evidence under the relevant owner.

### Pass condition

No Occasion-specific profile, poll, or setup form appears. The host does not
manually enter fields Vesper already resolved, and no invitee is silently
enrolled.

## F09 — Correcting “ticket existed” versus “I went”

### Scenario and controlled evidence

The journey currently shows a Sorrento–Amalfi occurrence inferred from a ferry
ticket and temporal fit. The person says:

> I had the ticket, but I didn't take that ferry.

An independently sourced Amalfi hotel check-in remains valid.

### Authority

```yaml
gesture: correct
immediate_job: reconcile
use: explicit_owner_correction + ticket + dependent_lineage
retention:
  source_ticket: keep
  occurrence_claim: invalidate
  correction_receipt: keep
inference: recompute_journey_without_ferry_occurrence
audience: every_projection_previously_authorized_to_show_the_occurrence
action: apply_causal_reversal
treatment: T1
```

### ChatGPT documented baseline

**DOCUMENTED:** The user can correct ChatGPT's memory conversationally or in
the memory summary. Fully deleting knowledge may require removing every source
where it appears.

**NOT ESTABLISHED by the documented baseline:** dependency-aware repair that
retains the source, retracts only the false occurrence, and invalidates every
dependent projection and pending consequence.

### Current Vesper code envelope

**CODE-EVIDENCED:** Intake candidate correction includes `did_not_go`,
`delete_derived`, source deletion, owner scoping, workflow cancellation, and
receipt/readback foundations. The fixture grammar names “keep occurrence,
forget interpretation” and other granular paths.

**Gap:** full propagation through every Home, Places, Life, story, memory, and
pending consequence consumer is not yet certified.

### Target first turn

> **Corrected.** The ticket remains in your records as a purchased ticket; the
> Sorrento → Amalfi ferry occurrence and every timeline or connection derived
> from it were withdrawn. The later Amalfi check-in remains because it has its
> own source.
>
> 1 occurrence withdrawn · 3 dependent projections updated · View receipt ·
> Undo correction

### Receipt and repair

- The detailed receipt lists affected owners without exposing content to the
  wrong viewer.
- Undo restores the occurrence only as an inference unless the person explicitly
  confirms boarding.
- A pending action that depended on ferry arrival is cancelled or reauthorized.

### Pass condition

No false ferry occurrence survives anywhere, and no valid ticket or Amalfi
evidence is unnecessarily deleted.

## F10 — Use continuity now, write nothing new

### Scenario and controlled evidence

The person explicitly chooses a no-new-memory posture:

> Use my Italy context to compare these three cliff towns, but don't keep this
> question or change future recommendations.

The harness supplies a verified comparison packet for three towns and the
person's already-authorized Sorrento observation. The current turn introduces
no new personal artifact.

### Authority

```yaml
gesture: ask_under_explicit_scope
immediate_job: compare
use: existing_authorized_continuity + current_comparison_packet
retention: no_new_chat_memory_source_or_derived_claim
inference: turn_only
audience: private_owner
action: none
treatment: T0
memory_use_posture: continuity_read_no_write
```

### ChatGPT documented baseline

**DOCUMENTED:** A personalized Temporary Chat can use existing memories without
creating or updating them; a non-personalized Temporary Chat uses neither old
nor new memory. Unsaved Temporary Chats do not appear in history, subject to
the documented safety-retention window.

### Current Vesper code envelope

**CODE-EVIDENCED:** Admission supports `answer_only` and ephemeral processing
for shared sources. Concierge can constrain memory retrieval and has actor-bound
recall.

**Gap:** the app has no clearly evidenced conversation-level equivalent of
“use existing continuity but write nothing new.” Ordinary Chat persists and
background observation, fact, note, and reflection paths may still run.

### Target first turn

> **The visual resemblance hides three different structures.** Sorrento is a
> relatively level tuff terrace cut into a coastal wall; Town B occupies a
> resistant limestone edge; Town C faces an inland gorge rather than the sea.
> The useful comparison is not “dramatic cliffs,” but how each settlement uses
> the boundary: above it, along it, or across it.
>
> Used your existing Sorrento context for this answer only · nothing new kept ·
> Sources

### Receipt and repair

- The receipt is a use-time aperture, not a retained artifact.
- No new semantic receipt is written beyond the minimum non-content safety or
  evaluation record authorized by policy.
- “Don't use Italy context either” should rerun fresh if requested.

### Pass condition

The existing relationship with Vesper improves the answer while the request,
generated comparison, and interaction signals do not shape later output.

## F11 — Resolve Ask versus Bring without a classification step

### Pressure set

Run the same menu photograph through three entries:

1. attach it to “What does this say?” in Chat;
2. send it alone in Chat; and
3. invoke the operating-system share sheet into Vesper.

### Required transitions

| Entry | Gesture | Source lifecycle | Claim lifecycle | Treatment |
| --- | --- | --- | --- | --- |
| Question + photo | Ask | transient; technical retry only | none beyond turn | T0 |
| Photo sent alone | Point/Bring | retained privately | literal extraction plus provisional interpretation | T1 after value |
| Share sheet | Bring | retained privately | literal extraction plus provisional interpretation | T1 after value |

The medium is identical; the language and invoked affordance change the job.

### Pass condition

All three entries receive a useful translation or explanation before any
receipt. Only the latter two enter Life Source custody. No path asks the person
to choose “Ask or save?” before contributing value. An ambiguous paste inside
an active conversation falls back to T0 unless retention is the invoked job.

### Hard failures

- every attachment is permanently saved;
- every attachment requires a confirmation sheet;
- a share-sheet Bring disappears after processing with no custody receipt; or
- the Source becomes a restaurant visit, meal, or preference by implication.

## F12 — Expiry and resurfacing are separate

### Pressure set

The harness creates:

- one menu image used only for Ask;
- one ferry ticket deliberately brought into Life;
- one unconfirmed semantic candidate over that ticket;
- one current Home Opening based on a restaurant's availability;
- one prepared provider consequence; and
- one featured post-trip Status.

Advance the clock through processing completion, 24 hours of inactivity, seven
days, provider deadline, Occasion end plus 72 hours, and explicit Source
deletion.

### Required transitions

- Ask-only bytes leave custody after processing or the bounded retry window.
- Session state expires after inactivity and cannot shape a later unrelated
  conversation.
- The Opening and prepared action expire with practical or provider truth.
- The Status retires after seven days unless replaced or extended.
- The retained ticket remains retrievable while its unconfirmed candidate
  expires.
- Deleting the ticket invalidates dependent claims and projections; a cached
  Home or Life card cannot resurrect it.

### Pass condition

The person can still find an explicitly retained Source after its proactive
eligibility ends. Expiry requires no cleanup queue and produces deliberate
silence rather than a card asking whether to preserve every candidate.

## F13 — Recommendation, action, Occurrence, and Outcome do not collapse

### Pressure set

Vesper surfaces a restaurant Opening. The person views it, saves it, books a
table, receives provider confirmation, later has supported co-presence at the
Place, and eventually says, “I loved the handmade pasta, but the room was too
loud for this group.”

### Required causal ladder

```text
opening_id
  -> exposure event: product target, L0/L1
  -> save relation: object + situation target, L2
  -> booking Commitment: operational truth, L2/L3
  -> provider confirmation: provider truth, L3
  -> supported Occurrence: Place + people + time, L3
  -> authored personal/group-scoped Outcome: L3
  -> later viewer-specific projection: L4
```

The save may improve current ranking without creating “likes Italian food.”
The booking may activate logistics without proving attendance. The Occurrence
may enter Life without proving enjoyment. The authored Outcome may improve a
later restaurant decision for the named person/group while preserving both
the positive food judgment and negative acoustic fit.

### Pass condition

Every later effect can name the exact stage and evidence it used. No routine
post-visit review prompt is required. If the person corrects attendance, the
Occurrence and Outcome dependencies recompute without erasing the valid
provider transaction.

## F14 — Co-owned Occasion photograph

### Pressure set

Alice imports a photograph containing Bob and Cara. She keeps it privately,
contributes a projection to their Rome Occasion, then attempts to feature it as
a friends-visible Status. Bob asks not to be identifiable or located outside
the Occasion. Cara does not respond.

### Required transitions

- Alice remains custodian of the private original.
- The Occasion projection preserves Alice's authorship and its roster audience.
- Contribution does not create Bob's or Cara's personal Outcome.
- Bob's affected-person request removes his name, recognizable projection, and
  location from wider future views without deleting Alice's private original.
- Cara's silence does not become consent. The wider projection must omit,
  crop, blur, abstract, or remain private unless existing policy independently
  authorizes it.
- Public Place publication is a separate T2 boundary.

### Pass condition

Occasion participants can retain a truthful shared core while subjective and
private material remains plural. Conflict narrows the wider projection rather
than creating a negotiation assignment for the group.

## F15 — Inspect and repair a derived Home opening

### Pressure set

Home shows a Palisades weekend Opening because the person saved a Sorrento
cliffs comparison, is home in New York, has Saturday free, and the trail is
currently practical. The person opens “Why this?” and says the Sorrento item
should remain in Life but should not influence future suggestions.

### Required transitions

The explanation names concrete evidence and current conditions. It does not say
the person “experiences travel through thresholds” or display a global trait.
Life opens the Sorrento episode and supports distinct operations:

- retain the Source;
- retain or release the comparison interpretation;
- exclude the relation from resurfacing;
- detach it from an episode;
- correct Place or Occurrence; and
- delete the original.

### Pass condition

Excluding the relation removes dependent Home and Places ranking effects while
the retained Source remains findable. Life stays an episode/object navigation
surface, not an inference review inbox or personality dashboard.

## F16 — One Paris artifact, four social purposes

### Pressure set

Use one friend-authored Paris artifact in four operations:

1. Address it to one named friend;
2. Contribute it to a current Occasion;
3. Feature it as a friends-visible Status; and
4. Publish a governed version to a public Place.

### Required transitions

| Operation | Recipients | Permitted purpose | Forbidden automatic use |
| --- | --- | --- | --- |
| Address | named friend | attributable delivery and response | recipient profile, public reuse |
| Contribute | Occasion roster | coordination, shared attention, bounded recap | durable personal trait, followers feed |
| Status | chosen audience | limited-time social opening | live location, invitation authority, public Place truth |
| Publish | public Place viewers | governed public perspective | private Source graph, companions, hidden visit history |

### Pass condition

Changing audience never silently widens purpose. Each projection retains
author, evidence, copying/resharing posture, expiry, correction, and honest
revocation limits. The person chooses through human verbs rather than a policy
matrix.

## F17 — Narrow connected-service retrieval

### Pressure set

The person:

- forwards one hotel-confirmation email;
- shares one Google Maps Place;
- asks whether Saturday afternoon is free; and
- asks Vesper to compare the Place with the active Plan.

### Required transitions

- The forwarded email enters custody as one Source; Vesper does not scan the
  inbox or infer unrelated travel history.
- The shared Place becomes a governed Place reference; complete saved Places
  and location history remain unavailable.
- Calendar returns the minimum availability window needed for the question;
  event titles, attendees, and notes remain excluded unless separately needed
  and authorized.
- Retrieval permission does not grant claim retention, social projection, or
  write-back.
- Adding the Place to a Plan or changing the calendar is a separate explicit or

The answer materially benefits from infrastructure outside Vesper while the

## F18 — Plan-bounded monitoring ends cleanly

### Pressure set

For an active Rome departure, the person authorizes Vesper to monitor one
flight, route to the airport, weather, and coarse current location until the
travel Commitment resolves. The flight is delayed and Vesper adapts the
departure Move.

### Required transitions

- Monitoring is scoped to the named Commitment and affected people.
- Provider status updates the world and Plan; coarse location and weather
  update current situation only.
- A route adaptation follows existing mandate and leaves a receipt.
- Provider confirmation and lived departure remain distinct.
- Monitoring authority ends on reconciliation, cancellation, revocation, or

The live engine's capability is visible before and during the trip without

governed Commitment, relevant provider truth, Occurrence, and Outcome—not the
continuous sensor stream.

## 6. Cross-fixture findings

### 6.1 The primary current inconsistency is not Intake v2

Intake v2 already embodies much of the target doctrine:

- custody before interpretation;
- raw source and derivative separation;
- explicit truth mode and evidence locator;
- private, advice-only semantic candidates;
- blocked proposed capabilities;
- bounded retention modes; and
- precise correction paths.

The sharper conflict is the legacy Concierge memory behavior. Current prompts
tell the model to:

- record preferences, personality insights, emotional investment, and context;
- write observations immediately in the same turn;
- infer durable traits across turns;
- treat skipped options and patterns of silence as observation evidence; and
- use prior memory explicitly as the “compounding advantage.”

Some of that was rational under the legacy travel-assistant thesis. Under the
current product philosophy, it collapses occurrence, behavior, intent,
preference, identity, use, and retention. The fixture results should determine
the replacement policy, but no new input surface should copy this prompt model.

| Current seam | Code evidence | What the fixtures require |
| --- | --- | --- |
| Ordinary Chat memory | `travel-agent/backend/concierge/_prompts_skills.py`, `memory_tools.py` | Stop treating every useful signal as permission for immediate person-level synthesis |
| Intake semantic candidate | `travel-agent/backend/inbound/semantic_contract.py` | Preserve source binding, truth mode, blocked authority, and precise correction |
| Share-capture review | `travel-app/app/share-capture/index.tsx` | Move value before classification work; test private apply + receipt against confirm-first |
| Conversation admission | `travel-agent/backend/core/models/admission.py` | Carry the answer-only/no-write promise through the whole response path |
| Occasion consequence | `travel-agent/backend/api/routes/experience_graph.py` | Separate private preparation from the real invitation boundary |

This is one migration seam, not five unrelated feature fixes: every input path
needs the same contribution contract before its output is allowed to feed Home,
Places, Life, shared Occasions, or live action.

### 6.2 The target is not “save less”

The product would also fail if it answered everything ephemerally. Pointing and
Bringing must create enough private continuity for Home, Places, and Life to
become valuable. The distinction is:

```text
retain the source-bound contribution and its governed relations
not a synthetic verdict about the person
```

F02–F04 therefore retain more than a generic answer-only assistant, but with
less semantic overreach than the legacy memory prompt.

### 6.3 The receipt belongs after the contribution

The current share-capture language—“Vesper found one thing to keep,” followed
by Keep, Correct, or Remove—makes the user perform admission work before the
system proves value. The target order is:

```text
substance
  -> resolved object or state when helpful
  -> one consequence
  -> quiet scope and repair
  -> stop
```

F03 and F04 are the decisive derivation cases. The research supports private,
source-bound application with Undo because confirm-first makes the person do
classification work before receiving value. Later comprehension work may tune
receipt prominence; it should reopen the authority model only if people
materially misunderstand audience or real consequence.

### 6.4 ChatGPT is the capability floor, not the design judge

Current ChatGPT memory already covers automatic synthesis, files, connected
apps, source visibility, correction, and temporary read/no-write modes. See
[Memory FAQ](https://help.openai.com/en/articles/8590148-memory-and-controls-faq),
[Temporary Chat FAQ](https://help.openai.com/en/articles/8914046-temporary-chat-faq),
and [Dreaming](https://openai.com/index/chatgpt-memory-dreaming/).

That establishes what Vesper cannot claim as a moat: remembering details,
reading files, using connected context, producing personalized prose, and
offering a temporary no-write mode. A point-in-time head-to-head would mostly
measure model quality, account configuration, connector availability, and the
fact that target Vesper is not yet implemented.

The relevant inference is categorical. Vesper becomes structurally distinct
when the value depends on governed objects and consequences that remain coherent
across time, Place, people, surfaces, and correction. A general assistant may
later reproduce any one capability; the product thesis is the integrated object
and authority system, not a permanent feature checklist against ChatGPT.

### 6.5 Portfolio derivation

| Fixture | Structural classification | Required transition | Why it matters |
| --- | --- | --- | --- |
| **F01** | Table stakes | No durable change; current evidence produces a bounded answer | Live practical judgment must work, but does not differentiate Vesper alone |
| **F02** | Continuity-bearing | Explicit Point → private Attention trace + source-bound Place relation | The explanation is copyable; the governed relationship that later opens Home/Places is not merely prose |
| **F03** | Architecture-bearing | Ticket source → scheduled transport artifact + provisional journey binding | Separates purchased evidence from occurrence and supports later causal correction |
| **F04** | Continuity-bearing | Photos + authored observation → distinct source roles + bounded culinary relation | The mechanism is copyable; preserving it without psychography changes future value |
| **F05** | Content-bearing, not a moat alone | Existing known-to-person context constrains novelty; no automatic new write | Proves editorial quality; becomes Vesper-specific only through governed continuity |
| **F06** | Architecture-bearing | Provider evidence supersedes one access assumption and recomputes the private Plan | Turns information into one truthful operational state across surfaces |
| **F07** | Architecture-bearing | Friend-visible trace → revocable private projection preserving author and audience | Multiplayer context adds value without becoming a group mind or copying private meaning |
| **F08** | Architecture-bearing | Private draft Occasion → explicit invitations → independent participant states | Makes coordination a plural, governed object rather than a generated message |
| **F09** | Architecture-bearing | Owner correction invalidates occurrence and every dependent projection while retaining valid sources | Causal repair is a system property, not apology prose |
| **F10** | Trust infrastructure | Authorized continuity is read for one turn while every new write path is blocked | No-write is table stakes; enforcing it across Vesper's richer graph is necessary product integrity |
| **F11** | Contract-bearing | Affordance + language → T0 Ask or T1 private Source custody | Keeps input effortless without making every attachment memory |
| **F12** | Lifecycle-bearing | Natural expiry + TTL backstop → storage and influence eligibility diverge | Prevents stale candidates and cached projections from becoming permanent truth |
| **F13** | Architecture-bearing | Exposure → relation → Commitment → Occurrence → Outcome | Allows operational learning without laundering behavior into identity |
| **F14** | Multiplayer trust | Private custody → Occasion projection → affected-person narrowing | Preserves contributor ownership and interdependent privacy together |

The portfolio therefore should not be evaluated as eighteen equal “AI answers”:

- **F01 and F10** define trust and competence floors.
- **F02, F04, and F05** show how excellent content becomes compounding product
  value only when its continuity is bounded and non-creepy.
- **F03, F06, F07, F08, F09, F13, F14, F16, and F18** carry the category thesis
  because their value depends on governed state, causal learning, multiplayer
  authority, situated action, projection, or repair.
- **F11, F12, F15, and F17** certify the input, lifecycle, trust, and integration
  boundaries that keep that category thesis coherent.

This also sharpens the immediate-value claim. Vesper does not need every Chat
turn to create a durable object. It needs to know when an answer is enough and,
when an object is warranted, create the smallest truthful object whose future
consequences justify its existence.

## 7. Structural inference protocol

### 7.1 Four-part derivation

For every fixture, resolve four different questions:

| Layer | Question |
| --- | --- |
| **Assistant capability floor** | Which part is already ordinary memory, retrieval, generation, or tool use? |
| **Current code envelope** | Which Vesper substrate exists, and which legacy behavior conflicts with the new philosophy? |
| **Target state transition** | What object, truth, authority, projection, or consequence must change? |
| **Structural delta** | What value disappears if only the response prose remains? |

Use this derivation receipt:

```yaml
fixture_id: F00
gesture: null
assistant_capability_floor: []
current_vesper_reusable_substrates: []
current_vesper_conflicts: []
input_evidence: []
target_objects_before: []
target_objects_after: []
truth_transition: null
authority_transition: null
surface_projections: []
repair_dependencies: []
value_if_prose_is_copied_elsewhere: null
structural_delta: null
hard_failures: []
```

### 7.2 Structural tests

Apply five tests to the portfolio:

1. **Prose substitution:** if the target paragraph pasted into a generic chat
   preserves all value, the case is content quality rather than category
   differentiation.
2. **Consequence dependency:** if value depends on a truthful Life object,
   current Place state, future Home opening, shared Occasion, or live action,
   the underlying state transition must be named.
3. **Cross-surface invariant:** the same source, claim, authority, and correction
   must survive Chat, Home, Places, Life, and social projections without each
   surface inventing its own interpretation.
4. **Authority symmetry:** retrieval cannot shed the source author's audience,
   privacy, revocation, or affected-person rights.
5. **Causal repair:** correcting or deleting upstream evidence must recompute
   every dependent projection and cancel or reauthorize pending consequences.

### 7.3 Permission ruling

The research and product structure are sufficient to choose the default:

| Situation | Ruling |
| --- | --- |
| Ask with no request to retain | **T0:** use authorized continuity, answer, write no new personal state |
| Explicit Point or clearly owned Bring; private and reversible | **T1:** create source-bound private state, deliver value, then show scope + Correct/Undo |
| Ambiguous Place, time, owner, Occurrence, or Occasion | Keep the source and a provisional interpretation; ask only when resolution changes truth or consequence |
| Audience, affected person, provider, spend, public, sensitive inference, or weak reversal | **T2:** prepare privately and preview the exact boundary before crossing it |

This is not “create everything and let the person clean it up.” T1 is permitted
only because it retains an authored source or bounded interpretation, keeps it
private, forbids person-level inference, and makes causal repair cheap. The
legacy memory behavior does not qualify.

Later comprehension research should tune the receipt and repair affordances. It
is not required to choose the architecture, and it should not turn contribution
into a preference survey.

## 8. Decision rulings

### Ruling A — Point/Bring default

Adopt private source-bound application with a quiet receipt for unambiguous,
reversible Point/Bring gestures. Do not require approval before Vesper has
provided value. Escalate only the unresolved truth or material boundary.

### Ruling B — Vesper differentiation

Do not claim differentiation from F01 or personalized prose alone. Across the
portfolio, Vesper's structural thesis is the combination of:

- evidence-bound objects and explicit truth states;
- situated projection across Home, Places, Life, and Chat;
- governed consequences instead of suggestions alone;
- multiplayer authorship and affected-person authority; and
- causal repair across derived state.

Each differentiated fixture must depend essentially on at least one of those
layers. The complete portfolio must exercise all five. Better copy alone does
not pass.

### Ruling C — immediate value

At least F01, F02, F03, F04, and F06 must be complete without a trailing user
question. F08 may ask only at invitation send. F09 may finish with a receipt.

### Ruling D — architecture

The same authority, receipt, and repair semantics must survive personal,
artifact, operational, social, Occasion, correction, and temporary cases. Do
not create a separate ingestion philosophy for each fixture.

### Ruling E — lifecycle, learning, purpose, and connectors

Adopt the [structured contribution-use-grant
decision](../decisions/2026-08-29-adopt-contribution-use-grants.md). Source,
claim, and projection lifecycles remain separate; Outcome learning names its
target and causal stage; multiplayer use is purpose-bound; and connected
services begin as narrow Source and action adapters.

## 9. Recommended sequence

1. Treat F01–F18 as a requirements matrix and complete the four-part derivation
   receipt for each—not as eighteen demos to build separately.
2. Keep the promoted Ask/Bring, lifecycle, causal-learning, purpose, and
   connected-service rulings aligned across interaction and consequence canon.
3. Enforce one shared contribution contract across ordinary Chat, inbound
   Intake, Occasion contribution, behavioral producers, connectors, and
   correction.
4. Replace or constrain the legacy Concierge memory prompt before it can feed
   the new Home, Places, and Life surfaces with person-level inferences.
5. Plan an architecture-spanning implementation tranche that exercises private
   Source admission, immediate contribution, scoped learning, purpose-specific
   projection, connected retrieval, and causal repair across multiple fixture
   families.
6. Use later usability work only to refine whether receipts, scope, and repair
   are legible and quiet enough.

This is not a “prove one behavior loop” strategy. The fixtures are a comparable
portfolio used to derive shared input architecture while preserving the whole
product.
