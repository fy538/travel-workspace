## 3. The language worth retaining

Working description: **a warm, readable personal field journal with precise
practical controls**. This is an internal design description, not new canonical
marketing language. It must accommodate everyday life, not imply a travel journal
is the whole product.

1. Continuous warm paper makes a screen one inhabited space.
2. Serif carries substantial reading, observation, identity and human words.
3. Sans carries operation, navigation and practical scanning.
4. Mono carries short coordinates: time, date, source and factual stamps.
5. Containment is selective and marks a coherent object, not only an urgent task.
6. Sparse color and quiet rules establish hierarchy without dashboard chrome.
7. Material selects a useful composition: original, sequence, method, comparison,
   map, record or practical arrangement. Do not flatten these into a generic body.

The four product moves remain distributed across roots. Home/Places receiving,
Life retrieval, Entity identity and Plans practical care need not have identical
layouts to belong to the same product. Social is a cross-root experience, not a
fifth root or a separate visual brand.

### Each project's strongest contribution

| Project | Reusable contribution | Intentional difference to preserve |
| --- | --- | --- |
| Home | Rich receiving hierarchy, ordered possibilities, methods, comparisons, reading previews | Strong orientation and selective prominence across a generous scroll |
| Places | Geographic pockets, time bands, place shelves, access comparisons, situated reading | Wider exploration and spatial relationships |
| Life | Four-lens index, precise retrieval, records, source-specific originals | Denser indexing and stable original/version identity |
| Social | Original-first reader, attribution, human reply, guest hospitality | Human authorship and room for actual photographs |
| Plans | Readable arrangement, hanging time column, collections without artificial timing, contextual assistance | Practical sequencing without a management dashboard |
| Entity | Stable shell, photographic presence, factual pairs, sourced purpose-responsive reading | A destination page rather than another feed |

## 4. Observed alignment and drift

### 4.1 Shared namespace is not shared implementation

All six exported `_ds` manifests and bundles are byte-identical. The bundle is
342 bytes and initializes an empty namespace. Manifest `components`, `tokens`,
`fonts` and `globalCssPaths` arrays are empty; card names are reference entries.
This proves the exports do not contain a functioning shared component library;
it does not establish what is available inside the original Claude workspace.

Home, Places and Social have byte-identical 8,323-byte `_kit/board-kit.css`
files. Selected phones also carry local inline CSS that differs from this kit.
Plans uses `kit/plans.css`. Life/Entity depend heavily on board-local styles.
Copying a common name or stylesheet comment is not an anti-drift mechanism.

### Maintenance model

- One shared-system owner reconciles common changes; product owners continue
  composing their own experiences and may propose a justified variant.
- Consumers reference a reviewed version with component IDs and dependencies.
  If true linking is unavailable, use generated/versioned copies with provenance
  and a detectable diff, not six hand-maintained forks.
- A product exploration may try a local exception marked proposed. Successful
  shared changes land in the library, then affected consumers update together.
- Require review for new meaning or interaction, not every ordinary token fix.
  Avoid a central approval bottleneck for content, layout inside accepted
  compositions, or routine implementation corrections.
- Do not move the 108 historical boards into the library as equally active
  references. Keep historical rationale in place and exclude it from selection.

## 8. Execution sequence and checkpoints

### Package A — select the reference set

Record project/revision, exact canvas and phone frame, status, viewport, fonts,
assets, shared dependencies and intended native receiver. Include inherited
styles. Archive/proposal material remains discoverable but cannot be selected by
accident. Do not make fresh full-world mockups for this step.

Record **visual selection** separately from **behavior-reference status**. An old
appendix may preserve valuable draft/recovery semantics without being a current
visual donor. Give selected phone roots stable identifiers (or a reviewed
equivalent capture adapter) that the existing exporter can resolve unambiguously.
Do not use a full board or a viewport-body fallback as a substitute for an isolated
selected screen. See section11.4 for the observed export gap.

### Package B — consolidate shared foundations and compositions

Populate the existing library where possible. Prioritize full-original reading,
shared controls, materials, shell, typed-original reuse and large-text reflow.
Keep contextual density variants and Entity's purposeful identity treatment.
Resolve small numerical differences centrally; escalate only genuine taste or
meaning conflicts. The founder should not inspect every radius.

**Checkpoint:** compare equivalent objects/actions, not six unrelated beautiful
screens. Review original → opened reader → Life retrieval; guest invitation in
Social/Plans; place preview → Entity; typed ticket → direct retrieval.

### Package C — apply to the existing six projects

Subsequent work, after the Stage 1 review in section 12. This package is not
authorization for the first shared-project assignment to edit six originals.

Update selected canvases and their component indexes to consume the shared
release. Correct missing dependencies and labels; preserve content richness and
purpose-specific layouts. Verify consumer exports actually contain or resolve
the components. Do not claim alignment from an identical namespace string.

Each project returns exact changed frames, consumed library revision, remaining
intentional variants, and representative normal/narrow/large-text renders.
No need to restyle every historical canvas or re-run product-policy debates.

### Package D — calibrate native translation

Map selected refs to registered native surfaces using the existing mobile visual
QA workflow. Use stable content and equivalent viewport/font conditions, then
test realistic variation. Render → compare → fix shared causes → recheck affected
consumers. Match design intent perceptually across browser/native; do not demand
pixel equality across different font/rendering engines.

This package is subsequent implementation work, not performed by this document.
Use affected Task Intake/contracts and native tests. Do not restart Integration
or change current runtime ownership by implication.

### Exit criteria and non-goals

- Shared components/styles are actually reused or versioned with detectable drift.
- Equivalent originals/actions retain recognizable identity across roots.
- Foundations have one current mapping; purposeful differences are named.
- Large text reflows type and leading; meaningful facts remain readable; real
  touch targets, safe areas and keyboard behavior are checked in native later.
- Selected references are wired to existing QA; config/test success is not a
  visual or participant verdict.
- Full-stack work continues. No exhaustive copy polishing, full rebrand, universal
  card, new root, mandatory loop, asset completion for all screens, or cinematic
  motion system is required to finish this bounded consolidation.

### 11.1 Finding and evidence boundary

The shared-library recommendation stands. The larger omission in the initial

For these designs, it must also preserve what a component does while information
arrives, a person responds, a save is unresolved, or the person returns from

All six HTML-set hashes still match section2: 108 boards, no new export delivery.
The second pass covered source/index/state references across all six projects,
with additional browser inspection of Home12, Places07, Life05, Social02,
Plans09 and Entity05. Those captures included component specimens and annotated
storyboards as well as consumer frames; they are not promoted native references.
Rendered samples used the actual fonts. A bounded synthetic long-name diagnostic
was performed only in an ephemeral browser page and did not modify the export.

The conclusions below distinguish observed defects, missing consolidation work,
and useful treatments already present. No claim is made that every remaining
interaction or every frame has been tested.

### 11.2 Preserve state behavior already designed

Several important states exist but are not yet organized as shared recipes:

| Existing source | Behavior worth retaining | Shared-system consequence |
| --- | --- | --- |
| Home12 stale/provider-unknown/import-pending | Stable material remains available; volatile facts retain their timestamp or withhold a number; partial import does not invent completion | Loading and uncertainty belong near the affected information, not automatically in a page-wide error card |
| Places07 map-unavailable/pending | The failed map slot changes locally while the rest of the field remains usable; progress sits near the question | A media failure and a failed query are different states, not one global loading template |
| Life05 partial/no match | The query and filters remain; the answer names the record's limit and offers optional assistance | Empty search is not an empty account and should not trigger onboarding or archive-filling homework |
| Social02.5 contextual reply | The original and human recipient remain visible while words are composed; Send is distinct from private Ask | The reply recipe needs original context, recipient, editing and result variants, not just a styled field |
| Plans09 J2b / appendix90 J2c–J2g | Keyboard expansion, retained words, pending navigation, confirmed failure versus unknown outcome, return and scoped Undo | Build the interaction lifecycle from existing examples; do not invent another coordination workflow |
| Entity05 temporary failure / unsupported stop | The candidate stays in place; temporary failure has retry, unsupported does not | Retryability is part of the state contract, not a stylistic button preference |

These are documented or illustrated behaviors, not all exercised interactions.
Plans90 explicitly says its consumer copy predates the subtraction pass and that
some keyboard, resume and read-only paths are illustration only. It must be a
**behavior reference**, not a wholesale visual donor.[^dl2-1][^dl2-2][^dl2-3][^dl2-4][^dl2-5][^dl2-6]

Recommended minimal recipe states are: resting, inspecting/editing, submitting,
known success, confirmed non-application, unresolved outcome, interrupted/resumed,
and unavailable input. Apply only states meaningful to that component. A reading
preview does not need a submit state; a provider-unknown fact does not mean an
owner mutation failed. Keep system bookkeeping outside the ordinary consumer
surface and reuse the concise selected treatment.

### 11.3 Selection and navigation need explicit shared treatment

**Selection is not one semantic operation.** Life's Time/Places/Threads/People
controls change the view; Life05 filters constrain retrieval; a Plans date rail
chooses a day; Social02's audience choices prepare disclosure. They can share
low-level selectable-control construction, but not an assumed effect or one
universal segmented-control layout. The shared library needs labeled view
switchers, filters, temporal selectors and audience selectors as named usage
variants. Their state labels and accessibility semantics must match the actual
job. This adds no preference questionnaire or new user-facing mode.[^dl2-3][^dl2-4][^dl2-7]

LifeR0's miniature state grammar also has a local premise: objects in Life are
already held, so an absent exception dot needs no held label. Do not generalize
that absence into a global claim about every preview elsewhere in Vesper. A
shared silhouette is not authority to infer retention or participation.[^dl2-7]

**The return is part of the composition.** Social06 explicitly restores the
original's scroll after receiving or replying, and carries question/form context
through private Ask. LifeP3's captured-day receiver remains in Home's stack when
opened from Home, although Life owns the reader. Plans09's keyboard-expanded
sheet keeps the target and field without opening another nested sheet. The
shared receiver specification should therefore record entry context, dismissal,
active root, restored scroll/focus, and draft behavior where relevant—not merely
which screen opens next.[^dl2-8][^dl2-9][^dl2-5]

This does not mean every receiver must show the same chrome. A verified guest
link intentionally has no app tab bar; Entity may use photographic overlay
controls; a root keeps its own orientation. Share construction and predictable
behavior while retaining those purpose-specific shells.

### 11.4 Selected frames are not yet directly addressable by the existing exporter

The 108 top-level HTML sources contain neither `data-screen-id` nor literal
`data-dc-slot` roots. A fresh browser check of one primary board from each project
also found zero roots for both the preferred selector and the exporter's
`[data-dc-slot] .dc-card` fallback. These sample documents are wide design boards,
not single phone-sized pages.[^dl2-10]

The existing native reference exporter discovers exactly these roots. This was
a source/DOM compatibility check, not an executed claim that every invocation of
the exporter fails; an explicitly supported future adapter could supply them.
Do not confuse this limitation with native rendering failure.

Package A should require:

1. A stable ID for the selected **consumer frame**, distinct from board ID,
   annotation wrapper, viewport marker and component-study label.
2. Isolation of that frame at a known logical width, with no annotation/canvas
   chrome or unexplained downscaling.
3. A deterministic font/asset/dependency manifest and an explicit ready state.
4. Capture selectors that fail visibly when the chosen frame is absent or
   ambiguous, rather than silently capturing the first board element.
5. Normal and variant captures that share the same object/content baseline.

Update authoring/export support or add a reviewed adapter through existing QA.
Do not hand-crop each future export or use viewport-body fallback on a wide
multi-screen board. No new visual-QA framework is required.

### 11.5 Provenance is another reusable presentation family

Sources already appear in several forms: a Home Why-this inspection, dated world
facts in Places, original source access in Life, author plus listing plus gallery
material in Social, time/evidence attached to a Plan row, and inline citations
or human references in Entity. These are not interchangeable decorative stamps.
The underlying distinctions deserve a shared **attribution and evidence** family:

- Author identity and audience where needed for interpretation.
- Source/freshness attached to the fact it qualifies.
- Inline reference and an adequately sized inspect action.
- Original source versus generated reading/version.
- Changed or unavailable material without rewriting the original's identity.

Use compact or expanded variants according to the reading context. Do not make
every unit expose an audit table, or make an inspection screen mandatory before
asking a question. Home12 is partly a proposed/older donor; its statement that
secondary questions must route through Why-this must not override the selected
Home15 direct-question treatment.[^dl2-1][^dl2-4][^dl2-9][^dl2-11]

This addition supports the product's value without adding operational chrome.
The purpose is to avoid six unrelated tiny source-stamp implementations and to
keep human authorship recognizable when the object moves between roots.

### 11.6 Test media and content variation, not only selected fixtures

The static examples establish useful visual hierarchy, but many human images are
still landscape stand-ins and many labels use short fixture names. Library
calibration should include a bounded variation set using the same compositions:

| Variation | What to check | What not to do |
| --- | --- | --- |
| Short and long human originals | Full-reader versus excerpt rhythm, paragraph width, visible authorship | Impose Social's22/30 on every excerpt or italicize an original because it entered through Life |
| Longer person/place names and action labels | Wrapping, target size, preserved recipient and subject | Invent truncation merely to match the short fixture's height |

| Document/evidence image | Legible whole source or explicit detail access | Apply editorial photographic grading to documentary evidence |

| Variable facts or incoming content | Stable current reading and local update treatment | Re-rank/rebuild the screen under the person's finger merely to look freshly personalized |

This is a verification portfolio, not a request for new content categories or a
complete asset library. Source-specific media guidance already exists; what is
missing is consistent consumption and representative calibration.

A small contrary result matters: replacing Social02's `Send to Maya` with

content-resilience certification. Do not manufacture defects to justify a larger
redesign.

Across these examples, check:

1. **Hierarchy and adjacency:** section title, content title and source stamp
   have different roles; two neighboring sections do not become indistinguishable
   text or repetitive mono headings. Different card lifts have a reason.
2. **Content density:** brief items stay brief, substantial outputs remain useful,
   and added wrappers do not consume the space formerly occupied by value.
3. **Disclosure and ending:** an overview contains initial value; deeper reading
   adds depth, not the withheld answer. The page can end without an input request.
4. **Responsive content:** normal/narrow/large-text, long labels and varied media
   preserve the target and meaning; never shrink text merely to fit a specimen.
5. **Update stability:** incoming content, withdrawal, late evidence and return
   preserve relevant identity, scroll and drafts without regenerating the page
   under the person's attention. Policy-pending examples stay labeled.
6. **Visual semantics:** planned, confirmed, occurred, sampled, attributed and
   generated material do not become equivalent because they share paper and ink.

These are bounded design acceptance checks, not a request to improve every
sentence, acquire a complete photo library or prove production runtime behavior.

show how much of that language resides in the composition between components,
not only inside them.[^coverage-1][^coverage-8][^coverage-9]

## 14. Deeper coverage check — specimens, controls and transitions

### 14.1 Revised assessment

**We have broad coverage of the product's reading and composition language,
but incomplete demonstrated coverage of its operating controls and transitions.**
Section 13 is a useful taxonomy. It is not yet a complete shared-component
specification, and its 21 family names should not be used to declare coverage
closed. In particular, “sharing,” “source inspection,” “selection” and
“contextual assistance” each conceal several distinct design obligations.

The most consequential gap is not another kind of Home card. It is the space
between a convincing resting screen and the person's next interaction:
choosing a recipient, changing a scope, selecting originals, opening a source,
correcting a result, leaving mid-request and finding the same context again.
Some of these are already drawn elsewhere in the six projects. Others are
described only in annotations or represented by a door whose destination is
not established by the reviewed specimens.[^detail-1][^detail-2][^detail-3]

This changes the consolidation assignment, not the product architecture:

- **Reuse existing transition donors** before asking a designer to invent them.
  Plans' appendix contains differentiated recovery states; Home has source
  inspection; Life has direct refinding; Social has a sender's own view.
- **Name small missing subpatterns**, not new feature projects. A selected-item
  toolbar or a recipient result row belongs in the shared controls canvas.
- **Keep product decisions separate.** A guest verification study, independent
  retained copy or following agreement remains proposed where its owner has not
  adopted it. Drawing reusable controls does not grant the capability.
- **Do not make users operate the model.** Most clarification and correction can
  remain language-based. A bounded direct choice should exist when it is simpler;
  an object page should not acquire a permanent form for every available action.

### 14.2 Evidence boundary and method

This follow-up used the unchanged six-export baseline in section 2, the
108-board inventory, extracted source text, and targeted deeper inspection of
the component/state boards below. It did not visually inspect every frame on
every historical board. Negative findings mean **coverage not established by
the reviewed specimens**, not proof that no similar design exists anywhere.

Home 12. Four captures were visually inspected for this follow-up: Life's

and opening/return material; Life P1/P2/P3; Social 03/04/08; Entity 04/05/10/12;
and Home 11/12. These are design studies, not verified native interactions.

The ledger distinguishes:

- **Drawn:** an identifiable specimen supplies visual anatomy.
- **Partial:** a specimen exists, but a meaningful next state/control is absent
  or only described in the inspected material.
- **Behavior donor:** useful rules/states, not selected customer-facing styling.
- **Proposal:** useful exploration under an unresolved or unadopted decision.

These labels can coexist. Separately record whether a shared implementation
exists, consumers adopt it, and interaction has been exercised. None follows
from “Drawn.” There is no defensible single percentage-complete metric here.

### 14.5 What to add now, what to leave alone

**Stage 1 remains bounded.** Keep the four comparisons and two full scrolls.
Give each comparison one meaningful continuation instead of expanding into a
large new journey portfolio:

1. **Human original:** arrive → open exact material → choose Reply or private
   Ask → return. Include an unavailable-original variant using existing donors;
   do not add a new independent-copy agreement.
2. **Invitation/share:** select or correct one eligible recipient → inspect the
   actual outgoing material → send/leave → readback. Reuse the same recovery
   primitive for a pending/failed result. Guest verification remains a separate,
   labeled dependency if that branch is not adopted.
3. **Place:** origin candidate → resolved or sparse page → one requested-check
   state → return. Keep the existing purpose-responsive destination; no new
   place-page redesign or booking flow is needed.
4. **Original/ticket:** direct search result → original/source → return to the
   same query. Add one selection-state specimen from Life 04 beside it so that
   Select/Delete selected is not merely a pair of labels. A destructive action
   is a design specimen only, never an instruction to delete real material.

Use the shared workbench to show these transitions; simple state switching is
enough for design review if explicitly labeled simulated. Prioritize actual
reuse and legibility, not a production backend or every failure permutation.
The common pending/failed/unknown/draft states can live once in the controls
canvas and be referenced by consumers, rather than drawn six times.

Every ledger row must have a disposition at Stage 1 handoff. **It need not have
a new implementation then.** Existing selected donor, targeted addition,
owner dependency, proposed capability and later native check are all legitimate
dispositions. Name an owner and trigger for remaining work. This keeps coverage
honest without making a complete design system a prerequisite to continuing
full-stack engineering.

The six project handoffs carry local donor/gap instructions through the
[owner routing table](vesper-five-project-design-consolidation-2026-09-08.md#coverage-follow-through-and-owner-routing--september-10).
Use their named donors when building this package; return a shared definition
and version for each adopted pattern so that later consumer work is adoption,
not reinvention. These documentation updates do not mark any gap resolved or
authorize modifying the original design projects before the Stage 1 review.

Do **not** add a full composition editor, new standalone social feed,
notification center, account settings suite, complete audio/video system,
universal map tooling or a booking flow merely to make a coverage spreadsheet
look complete. Dedicated Chat remains outside these six exports. Those areas
need coverage only under their own supported scope and owner.

### 14.6 Closure bar and sources

Coverage can be accepted for a selected experience when its manifest identifies:

> visible entry → relevant control/state → useful result → return/leave →
> selected donor or explicit gap → reusable definition/version → consumer owner.

For a genuinely read-only unit, consuming it and leaving is a complete ending;
do not manufacture a CTA or receipt. For an actionable unit, a button label or
annotation is not the missing destination. For an unavailable capability, a
truthful bounded ending can be complete without inventing support.

**Bottom line:** the six projects are enough to ground a coherent shared design
language. They are not yet evidence that every needed interaction has been
specified. The next useful work is extraction plus a short set of missing
control/transition specimens—not another general visual exploration.
