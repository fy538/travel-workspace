# Complete-system integration reference

This is supporting technical guidance, **not a second roadmap or dispatch
queue**. The [program roadmap](vesper-program-roadmap.md) owns current priority,
assignment and baseline. The original September 5–22 plan, I0–I6 packages,
CV milestones and receipts are preserved in the
[integration archive](../archive/complete-system-integration-history-through-2026-09-25.md).
Their open obligations remain relevant; their old status and sequencing do not
become current merely because a package links to them.

## Retained architecture and integration obligations

Trace a consumer outcome through **producer → canonical owner/read → selection
and composition → mobile presentation → action/readback → return/later use**.
Implement the broken connection at its owning layer. Do not solve a receiving
gap with a parallel store, feed, generator or authority model.

The recovery baseline is merged; the subsequent Home candidate is published in
three open PRs, rechecked September 28. The reading, exact-context Chat and
practical-state/action follow-ups are locally committed with bounded tests and
native self-review, not part of the published candidate's coordinated gate. Follow
the program's exact tuple and current lane owner rather than redispatching
completed connections from an older local main. Backend `539edb00d` and app
`af8a126af` add bounded owner previews and clearer Returned/recovery copy.
The connected H1 checkpoint is reached, but product acceptance is incomplete:
Urgent lacks owner-backed alternative trade-offs, social hierarchy has residuals,
and real recurring supply remains unverified. A passing Chat-continuation capture
does not close a different Urgent capture's P1. Capture/share foundations may
proceed under the program while these named gaps remain open; do not rebuild
already connected Source, original, practical and Chat paths.

The accepted [September 26 multiplayer direction](../decisions/2026-09-26-multiplayer-direction.md)
and [September 27 one-composer decision](../decisions/2026-09-27-documenting-core-loop-and-one-composer.md)
shape the next capture/share package. Before affected runtime changes, reconcile
their named contribution, Chat, social and product owners. One horizontal
composer must reuse Source custody, candidate lifecycle and relationship owners,
not become a universal artifact store. Deliberate share-plus-question now has
an accepted Bring-plus-Ask amendment; casual-question continuity, autonomous
type evolution and thread/status-triggered offers are not adopted by this plan.

## Live engine stays inside the product

The engine is not only disruption repair during a trip. It should make ordinary
local time and anticipated plans more usable through supported current facts,
timing and permitted context. Every affected package should name what input
changes judgment, which surface changes, what action is allowed, and how it
stops or repairs. Reading value can remain complete without a subsequent action.

For a live case retain purpose, known/unknown conditions, source clock, trigger,
treatment, permitted effect, reevaluation and stop condition. A Keep does not
create a durable watch. Being in Live posture does not alone justify suppressing
the rest of Home. New delegated action, external effects and later private use
remain subject to their owner decisions, not implied by this plan.

## Whole-product coverage without a giant acceptance bottleneck

Preserve the portfolio: ordinary week/open time; return from travel with life
continuing; practical change; authorized waiting/release; social perspective and
shared arrangement; sparse/unavailable context; correction and later refinding.
The detailed [historical portfolio](../archive/complete-system-integration-history-through-2026-09-25.md#6-whole-product-acceptance-portfolio)
records the intended behaviors. It is not evidence that all are implemented.

Each package selects the affected cases and verifies them at their appropriate
layers. Do not demand a full multi-surface device rehearsal after every small
edit. Do not postpone all cross-system verification to the end either: review
shared contracts when they change, and run the required coordinated gate before
publication. If a service or device is unavailable, complete independent code
and focused verification while retaining the unverified boundary explicitly.

Visual polish is part of completion: layout, content hierarchy, density,
interaction, accessibility and return should meet the accepted reference for
the changed surface. A new Downloads export is design input until adopted;
registered external references must be verified for a parity claim. A passing
renderer test is not native visual acceptance, and a fixture capture is not
provider-backed runtime evidence.

For Home specifically, the current `home-root` registration includes selected
02/03 first-viewport `designRefs` but still judges doctrine. Those reference
pairs have different content/dates and do not establish full-scroll parity.
H1 records the remaining native findings and reference boundaries. The older
Trips Home/Places Workspace bundle does not automatically adopt newer studies,
grouped-photo ownership or reply behavior.

## Package handoff and integration

Use the active package linked from the program, not an assignment copied from
this archive. Give one implementation owner authority to complete ordinary
repairs and reviewer findings within scope. Separate workers only on independent
files/outcomes, with one owner for shared schema and navigation changes.

Handoff reports changed behavior, exact revisions, focused checks and evidence
limits, unresolved decisions, and branch/worktree disposition. Land a coherent
reviewed package at its natural dependency boundary. The existing lane tooling
and required `make verify` govern publishing; this reference introduces no new
tracker, approval tier, standing integration task or always-on polling loop.
