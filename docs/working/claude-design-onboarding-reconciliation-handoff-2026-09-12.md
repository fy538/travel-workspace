## Outcome and important reconciliation

**Sequence updated later September 12:** Chat and You & Trust are now new,
visual-first projects. Onboarding may explore independently, but its selected
entry must follow the founder-selected Chat direction; do not inherit the old
composer arrangement as the only option. Effective authentication and privacy
boundaries below remain unchanged. No new onboarding project is requested.

Someone with almost no history receives useful understanding or practical help
from one thing in front of them. They need not import their life, recruit friends
or create a Plan. “Help me understand this” must be as welcome as “help me make
something happen.” The person may leave after the useful answer.

The old organic experiment gives a judgment before sign-in, then authenticates
to save. The current contract preserves a starter through authentication and
obtains the server-grounded response afterward. **Use the effective contract as
the baseline.** If proposing pre-auth AI, isolate that alternative and state the
service/account decision it needs; do not silently adopt it. Current mobile
already has an ordinary first-value starter: legacy trip/taste routes do not
prove travel is the default entrance.

## Bounded design assignment

Produce a selected current-entry canvas and a compact exception canvas using
the existing studies and Chat controls:

| Entrance | Show the complete consumer sequence |
| --- | --- |
| Organic question | Concrete starter or ordinary question → actual auth boundary → useful grounded answer → optional next step or leave |
| External share | Supported item from another app → preserved payload/words → auth when required → useful result under the invoked Ask/Bring meaning |
| Friend's offering | Exact legitimate preview → required identity/access step → useful receiving; no equivalent contribution or mandatory friend recruitment |

Include cancellation, retry, existing-account recovery, session/account mismatch
and truthful payload-loss handling. Show what survives authentication rather
than drawing persistence as if code already proves it. Never expose private
payloads to the wrong signed-in account.

For local help, show manually supplied geography as well as permission denial
and weak/unsupported locality. A remote query is not device location. Ask for
permissions when the benefit requires them, not as an installation checklist.

Reuse Home 04/14 cold receiving and Life 02's honest empty record from the
[snapshot](../design-archive/design-language-2026-09-11/README.md). Do not invent
a demo Home, mandatory tab tour or questionnaire. Show the four roots Home /
Chat / Places / Life only as useful destinations, never a required funnel.

Recipient guest access remains conditional on its actual selected service.
Social owns recipient semantics; onboarding owns entrance continuity. Neither
an invitation design nor an OTP field authorizes a new guest-access policy.

## Handback and stopping rule

- Mark the current sequence selected and old alternatives historical; provide
  a short change map from the three-root/pre-auth experiments.
- Link each entrance to the same Chat or receiving controls used elsewhere;
  state the supported input/auth assumptions and remaining decision owners.
- Show entry, useful result, exception and sensible exit, with no forced filing,
  setup or continuing use. Native auth/payload recovery remains unverified
  until exercised; realistic drawings are not service evidence.

Align with Chat's selected entry first; do not wait for every Chat detail or
hold unrelated engineering. This handoff changes no production route, auth
policy, retention rule or commercial offer. No new visual language is requested.
