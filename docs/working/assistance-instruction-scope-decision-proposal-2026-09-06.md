# Decision proposal: natural instructions with precise scope

## 1. Status and decision requested

**Proposed, not adopted or implemented.** The founder authorized this proposal
after the [scope research](vesper-useful-preparation-and-initiative-research-2026-09-06.md#11-follow-up-research-assistance-that-has-a-scope-not-a-permanent-mode)
and [competing-purposes week](situated-value-decision-matrix-2026-09-06.md#13-a-week-of-competing-purposes-changing-receptivity-and-repair).
Existing [Contribution and Consequence](../systems/contribution-and-consequence.md)
and [Memory and Preference](../systems/memory-preference.md) remain authoritative.
Approval of this document would settle product semantics, not select a schema,
activate a worker or certify a cross-root implementation.

**Recommendation:** interpret natural redirection as a scoped instruction about
assistance, not automatically a fact about the person. Support four cases:
this response; an explicitly named surface and period; a named episode/purpose;
and an ongoing, deliberately established default. These are review cases, not
four modes, tabs, gesture types or required storage classes.

The person should be able to redirect Vesper without managing its memory. Vesper
still chooses useful help from eligible context when no instruction is supplied.
Do not make explicit scope wording the price of receiving competent assistance.

## 2. Four scope cases

| Case and example | What changes | What does not change | When application ends |
| --- | --- | --- | --- |
| **This response:** “For this answer, keep it short” | Current answer depth, including continuations that finish that same answer | Later defaults, Home mix, saved interests and other work | When this answer is complete; retries preserve the same request identity, a new question is not a retry |
| **Named surface and period:** “On Home today, fewer things to decide” | Optional decision pressure on Home, with worthwhile reading, human material and practical access still available | Chat's ability to plan when asked; Places inventory; Life custody; important current consequences | Resolved end of the stated period, explicit revocation or an earlier authority/lifecycle end |
| **Named episode/purpose:** “For Saturday's family dinner, let me choose; just compare” | The viewer's private assistance for that identified dinner across relevant roots and continuations | Shared decisions, anyone else's preferences, unrelated Saturday activities and sending authority | The episode's applicable operational lifecycle ends, the purpose is explicitly replaced/released or source/use authority ends |
| **Ongoing default:** “For restaurant suggestions, usually start with one recommendation and show alternatives” | An admitted, correctable assistance default for restaurant suggestions | A current request for comparison, other domains, hard constraints, action/audience permissions | Explicit replacement, release, scope end or loss of authority; not an arbitrary engagement-based timeout |

The examples are proposed behavior. No receipt may claim a cross-root or durable
effect before the responsible owner has actually applied it. A request can have
several effects; resolve each through its owner rather than forcing the whole
utterance into one category.

### Ambiguity and truthful acknowledgment

Resolve the actor, referenced object, intended effect, reach and duration
independently. The current card or conversation can establish a clear subject
without another question. “Today” alone does not mean every root; “Saturday”
alone does not identify which of several plans. A quotation, imported document
or friend's instruction is not the viewer's preference.

- “Too long” usually warrants a shorter current answer, not a global preference.
- “Less planning; give me something to read” warrants useful reading now. Do not
  silently add a day-long Home rule if its reach is not established.
- A clearly broad instruction must not be artificially reduced to one response
  just because the persistent path is unavailable. Help now and state the
  unsupported future effect briefly where the person would rely on it.
- Ask once only when the unresolved scope changes a consequential write,
  future reliance or necessary effect. Do not make a scope picker precede value.

After actual success, suitable compact acknowledgments include “Short version:”,
“Fewer decisions on Home today,” or “For this dinner, I'll compare and leave the
choice to you.” A durable default can say “I'll use that approach for restaurant
suggestions,” with a contextual correction/control route. These are illustrative
receipts, not a new copy canon. Never say “updated everywhere” based on a prompt
change or before downstream consumers can honor the instruction.

## 3. Lifecycle and conflict decisions

### Applicability is not custody

Retaining an instruction's evidence does not keep it active forever. Ending
its influence does not delete an independently retained Source, original
conversation or saved idea. Conversely, an intended future duration cannot
override a shorter authorized source/use lifetime. The existing Ask and optional
history agreements do not change here.

For an explicit cross-root period, the proposed admission is only the bounded
authored assistance instruction and the minimal eligible references needed to
honor it—not the surrounding conversation, a mood inference or a new biography.
This is the precise extension requiring approval and owner review. Current
response/session adaptation can continue under the existing contract meanwhile.

### Resolve time once, revise deliberately

For “today,” resolve the end of the known local date using an established
timezone. Preserve that resolved instant rather than extending it because the
person changes timezone or reopens the app. Do not request physical location
merely to determine this; ask for temporal clarification only if needed to make
the promised duration meaningful. Without enough information, honor the current
job and do not claim a resolved cross-root period.

The session's 24-hour inactivity backstop is not the meaning of “today.” Neither
opening a root nor re-reading an instruction renews its duration. A background
expiry notification is unnecessary unless its absence would mislead someone
about accepted responsibility.

For a named episode, use its canonical identity and owner-defined operational
end, cancellation or release. A revised date follows that same owner identity
where the instruction was for the episode; a separately explicit fixed-period
limit remains fixed. Do not extend assistance into a reconciliation window
merely because evidence is retained there. If the owner cannot define the
needed applicability lifecycle, record that blocker before promising persistent
episode-scoped behavior. Scheduled end does not prove attendance or satisfaction.

### Override is different from replacement

First enforce actual source, audience, action and hard-constraint boundaries.
Within eligible assistance, apply the current explicit instruction and then
the applicable narrower instructions/defaults under the contribution contract.
Specificity only resolves overlapping instructions about the same effect; it
does not let private wording modify shared truth.

A local exception suspends the relevant default for that scope; it does not
delete the default. Explicit replacement or revocation supersedes the affected
instruction through its owner. A newer sentence about another subject cannot
overwrite it. Revision and retry checks prevent stale clients, queued work or
replayed events from resurrecting a superseded instruction.

When a temporary exception ends, recompute applicable assistance from current
evidence. Do not restore yesterday's exact composition, re-promote a postponed
activity or revive a separately canceled cue. Expiry is not a positive signal
that the person now wants the opposite behavior.

## 4. Cross-root effects and repair

| Consumer | Required behavior |
| --- | --- |
| Chat | Apply current redirection immediately; preserve object identity in continuations; acknowledge only actual owner effects |
| Home | Apply eligible treatment instructions during composition and receiving; reduce unwanted demands without emptying useful value or hiding material current consequences |
| Places | Apply relevant comparison/recommendation style to the same purpose while retaining authorized inventory and exploration; Home-only wording is not a Places-wide filter |
| Life | Keep originals and owned records refindable; support contextual inspection/release through existing controls without becoming the instruction writer or a new memory dashboard |
| Live judgment and production | Revalidate scope/revision at useful decision points and before delivery; distinguish presentation changes, replaced goals and explicit cancellation |

Repair follows the changed effect:

1. **Shorter expression:** reuse a valid result; do not repeat source research.
2. **Different current benefit:** remove unwanted prominence while preserving
   eligible depth and independently kept evidence. Sunk generation cost earns
   no right to present the result.
3. **Goal replaced:** cancel obsolete work where supported or suppress late
   delivery for the replaced purpose. Do not cancel unrelated work.
4. **Use restricted:** invalidate the disallowed dependent use, not the original
   by default. Source revocation and actual deletion keep their existing rules.
5. **Instruction expired:** stop applying that instruction; this does not make
   otherwise valid world facts or completed assessments false.

Differentiate response correctness from factual correctness: an accurate workshop
can be the wrong suggestion now. Do not rewrite its facts because the user wanted
reading instead. Preserve scroll and touch targets during receiving changes, but
never keep revoked/private content visible solely for visual stability.

An assistance preference does not grant work authority. The
[accepted bounded-production decision](../decisions/2026-09-06-bound-source-production-worker.md)
still excludes ordinary GETs, tab focus and app launch as production triggers.
“More ideas” does not authorize unlimited generation; “keep this” does not create
a watch. “Stop checking” must resolve an actual task/mandate and report its real
state rather than claim to stop monitoring that never existed.

## 5. Ownership and implementation requirements

**Logical ownership recommendation:** Contribution resolves the authored gesture
and authority; the existing governed context/memory domain owns any admitted
assistance instruction and its revision/lifecycle; canonical episode owners
supply references and lifecycle facts. Roots and prompt summaries are consumers,
not alternate writers. An episode association does not grant the episode's other
members access to the viewer's private instruction.

This does not certify a ready persistence/command owner. Before implementation,
Integration and the contribution/memory owner must name the exact existing
record, writer and reader that can enforce the semantics, or document the
smallest missing typed extension. Do not force temporary non-Plan help into a
Plan, durable personality observation or universal instruction store solely
because those are convenient. This review is a required engineering checkpoint,
not permission to create another memory system by default.

For a cross-root effect, preserve the minimum necessary authored basis, viewer,
subject refs, intended treatment, consumer applicability, temporal/lifecycle
bounds, authority, revision and correction lineage. Physical fields and endpoints
are not selected here. Resolve meaning with the model where helpful; enforce
eligibility, expiry, revocation and current revisions in the owner/read paths,
not only through prompt obedience.

Writes use the existing actor/target/revision/idempotency conventions. Apply and
read back before promising persistence. Partial consumer delivery is not global
success: either gate the cross-root promise until its required consumers are
supported or state the narrower actual effect. Account switches, offline stale
reads and late results cannot reuse another viewer's instruction. An unavailable
optional style instruction may fall back to ordinary assistance; an unavailable
authority check must not fall back to a privileged use.

Use existing change/repair delivery. Do not add a scheduler to expire instructions:
read-time eligibility and existing supported change paths must keep expired
instructions from affecting output. An already open root must also honor the
resolved boundary through its existing expiry/recomposition mechanism; waiting
for a new message cannot renew the instruction. This is consumer revalidation,
not a trigger for optional production. Any stronger proactive delivery requirement
needs its own named mechanism. No historical chat backfill or inferred preference
migration is authorized.

## 6. Acceptance cases and progression

| Case | Required observable result |
| --- | --- |
| Response-only instruction, then new question | Current answer changes; no unrequested future default |
| “Today” without established Home reach | Immediate requested value; no all-root mood change |
| Explicit Home/day instruction, then planning in Chat | Home reduces optional decisions; Chat handles the invoked planning task |
| Two episodes on Saturday | Instruction follows only the resolved episode |
| Private episode instruction | Relevant private continuations adapt; shared facts and other people's preferences stay intact |
| Temporary exception over an ongoing default | Exception applies locally; default survives without forced re-promotion afterward |
| Timezone change, midnight and reopen | Resolved boundary honored; no silent renewal or fixed 24-hour substitute for a local day |
| Episode rescheduled or canceled | Canonical identity/lifecycle checked; fixed-period limits preserved; no inferred attendance |
| Correction during queued production | Current scope/revision checked before delivery; obsolete work cannot restore the old goal |
| Presentation change after valid research | Reuse permitted substance; no unnecessary provider call |
| Source kept but recommendation use withdrawn | Original remains accessible; excluded use and dependent delivery are repaired |
| Duplicate retry and stale edit | One intended effect; stale revision cannot overwrite later correction |
| Offline, restart or viewer switch | No expired/revoked/cross-viewer influence or false global-success receipt |
| No correction or further input | Competent ordinary help still works; no preference-maintenance obligation |

After product adoption:

1. Map the four cases to actual writers/readers and lifecycle support under
   existing Integration I1/I3 and contribution/context work. Identify gaps before
   persistence or API changes; perform the normal generated-contract workflow
   if an API changes.
2. Implement owner correctness, then cross-root receiving with I1/I4. Keep
   production integration inside I2's accepted trigger/activation gates. Do not
   block independent useful answers or existing owner-backed value.
3. Review complete experiences alongside tests: can a newcomer predict what
   changes elsewhere and tomorrow, correct a misunderstanding once, and receive
   useful value without steering every step? Reassess if control requires more
   supervision than the assistance saves or if useful exploration disappears.

## 7. Approval boundary and non-decisions

Approval must settle the four scope behaviors, the bounded authored-instruction
admission described in §3, temporal/episode applicability, private ownership,
override versus replacement, and truthful cross-root receiving. Promote the
agreed text into an accepted decision and update the contribution/memory contracts
before implementing the new cross-root write path. A schema and migration review
remain separate; no grant is inferred from this proposal's existence.

This proposal does not adopt optional conversation-history reuse, retained loose
intent, passive personality learning, new monitoring, notifications, external
actions or generalized background production. It does not add a product move,
root, global mode selector or compulsory memory-management screen. Existing
permissions and supported local adaptation remain the baseline while it is reviewed.
